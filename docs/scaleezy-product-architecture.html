01What the product does

Bespoke tailoring runs on paper diaries, WhatsApp threads and the owner's memory. Scaleezy replaces that with a single record per client and a tracked production pipeline per garment.

Each boutique signs up and receives an isolated workspace. Inside it they build a client directory with body measurements and style preferences, take a custom order through a guided six-step intake, then follow that garment through a twelve-stage production workflow — each stage timestamped, attributed to a named tailor, and able to carry photographs and comments.

The owner sees revenue, order status distribution and staff workload on a dashboard. Masters and tailors see only the orders assigned to them. Every state change is written to an audit trail.

02Who uses it

Roles are carried on the staff record and drive both what the interface shows and which production stages a person is permitted to advance.

Role What they do What they see on sign-in
Owner Runs the boutique. Creates orders, manages the client directory, fabric and design catalogues, hires staff, sets pricing, configures the workflow. Full dashboard — revenue, all orders, all clients, analytics, settings.
Master Senior tailor. Supervises orders, drafts patterns, runs the quality-control inspection, conducts fitting trials, signs off dispatch. Assignments view — orders they supervise, with client measurements.
Tailor Constructs the garment. Starts and completes stitching, uploads finished-garment photographs and comments. Assignments view — orders assigned to them for stitching.
Client Does not log in. Exists as a directory record and as the recipient of order-progress notifications. —

Staff accounts are created automatically when a tailor record is given an email address. The owner account is created at boutique sign-up.

What happens when an order is created

Order creation — single transaction

1
Price is computedSix line items are summed, 5% tax applied. Delivery estimated at 15 days.
2
Order record writtenWith a collision-checked reference of the form T2B-YYMMDD-NNNN.
3
Twelve stages materialisedRead from the boutique's workflow settings. Created is marked complete; Measurements Completed too, if the client already has measurements.
4
Eight production tasks createdRouted to master or tailor by task type, each with a priority.
5
Audit entries writtenOne order event and one cross-module activity record.
6
Notifications generatedFor owner, client, and any assigned master and tailor.
7
Staff marked busyAssigned master and tailor flip to Busy.

The whole sequence is atomic — a failure at any point leaves no partial order behind. Stage transitions are wrapped the same way.

A Django REST API and a React single-page client, over one PostgreSQL database that is partitioned by schema — one schema per boutique.

Multi-tenancy

Isolation is structural rather than a filter applied in application code. Each boutique gets a PostgreSQL schema created at sign-up and migrated automatically; a query issued in one tenant's context physically cannot see another's rows. The shared public schema holds only the tenant registry and domain mappings.

Tenant resolution — every request, in order

1
HeaderX-Tenant-ID is matched against the registry. An unrecognised value is rejected with 400 rather than falling through.
2
TokenFailing a header, each schema is searched for the bearer token. Correct, but costs one query per tenant — see §11.
3
HostnameFailing both, the request host is matched against the domain table.
4
PublicOtherwise the connection stays on the public schema, which serves sign-up and login only.

Isolation across consecutive requests on a reused connection is covered by automated tests that interleave two live tenants and assert neither sees the other's clients.

Customer and Order both key on Customer; an Order belongs to exactly one client. Tailor attaches to an Order twice — once as stitching tailor, once as supervising master.

Standalone records

BoutiqueFabric and BoutiqueDesign are catalogue tables with no foreign keys — a fabric or design is copied onto an order by name and price at selection time, so later catalogue edits never rewrite historical orders. Notification and UniversalActivity are likewise append-only records addressed by role or module rather than by relation.

Notable design decisions

  • Workflow as data. The stage definition lives in a JSON column on boutique settings, not in code, so studios can differ without a deploy.
  • Stages materialised up front. All twelve rows are written at order creation rather than lazily, so progress is a simple count and the tracker needs no synthesis.
  • Measurement history is automatic. Saving a measurement compares against the last version and writes a new one only on change.
  • Two audit logs. A per-order event stream for the order timeline, and a cross-module feed for the boutique-wide view.
Modelling debt

Order progress is tracked in four places that must be kept in step by hand: order_status, the stage rows, current_stage_key, and each task's stage_key. Hand-maintained mapping tables in three files keep them aligned. Deriving status from the stage rows alone would remove a whole class of drift bug.

09Performance

The two read-heavy endpoints were rebuilt in July 2026. Both had been loading deeply nested object graphs, which at production latency exceeded the server's request timeout — the client directory appeared empty because the request was being killed before it answered.

EndpointBeforeAfterQueriesPayload
Client directorytimeout2.0s261 → 1119 → 28 KB
Dashboard5.4s1.3s90 → 2438 → 24 KB
Orders2.5s0.8s46 → 1476 KB

What changed. Query shape was fixed in the repository layer so every relation a serialiser reads is fetched in one pass. List endpoints now return flat rows and derive totals in SQL; the full object graph is fetched only when a record is opened. Regression tests assert that tripling the number of records adds no queries.

Remaining ceiling

Roughly 2 seconds of every response is now fixed overhead, not query cost: the API is hosted in a different region from the database, so each round trip costs about 190 ms against 53 ms from a co-located client. Moving the API to ap-southeast-1 would cut this several-fold and needs no code change.

10Implementation status

Included so nobody demonstrates a feature that is not there. Everything marked Live in §4 works end to end against real data. The items below do not.

Partial  Notifications are recorded, never sent

Notification records are generated correctly for owner, master, tailor and client — with appropriate copy per lifecycle stage, including tracking numbers and outstanding balances — and staff see them in the app. But there is no email or SMS integration: a record addressed to a client's email address is never delivered anywhere. The client-facing half of this feature is data only.

Partial  Style DNA is half derived, half placeholder

Of the seven fields shown on a client's style profile:

  • Real — budget band, size category, visit pattern, lapse risk and next action are all computed from the client's actual orders and measurements.
  • Placeholder — the colour distribution and style split are picked from six and four fixed strings by hashing the client's ID. They are not derived from any data about the client.
Defect

Because Python randomises string hashing per process, those two fields change every time the server restarts. The same client shows "Charcoal Black 90%" before a deploy and "Dusty Rose 60%" after. Anyone treating the style profile as a stable client attribute will be misled. Fix is a stable hash or, better, real derivation from order history.

Mocked  Draping preview

The fabric preview maps the chosen fabric's colour to one of six fixed stock photographs. No image generation or garment simulation takes place. It reads as a product visual, so it should be labelled clearly in any demo.

Partial  Appointments and quality control

Both have complete data models and working REST endpoints, but no interface. Appointments cannot be booked and QC results cannot be entered from the app — the scheduling and inspection features are backend-ready and front-end pending.

11Known gaps

Security

Open API — highest priority

Every business endpoint is readable and writable without authentication. Anyone who knows a boutique's schema name can read its entire client list — names, phone numbers, addresses, measurements and revenue — and can also write to it. The permission default was relaxed during deployment and never restored. This is the single item to fix before the platform holds real client data at any scale.

  • Credentials in version history. The database password and application secret key were committed to the repository. They have been removed from the current code and the database password has been rotated, but the history remains readable — the secret key still needs rotating.
  • Shared staff password. Every tailor account is created with the same bootstrap password. It is now configurable, but there is no invite or reset flow.
  • Cross-origin policy is open. Any origin may call the API. Restricting it is a single environment variable, already supported.

Scale

  • No pagination. Directory and order listings return every record. Fine at a few hundred; not at a few thousand.
  • Token-based tenant lookup is linear. A request without the tenant header searches every schema in turn. Cost grows with the number of boutiques on the platform. An index in the public schema mapping token to tenant would make it constant.
  • Region mismatch. API and database are in different regions — see §9.
  • Orders listing still carries unread data. Activity logs and stage histories are serialised into every order although no screen displays them.

Product

  • Client communication is the biggest missing piece. The notification content is already written; connecting a delivery provider would turn an internal log into the client-facing feature the product is positioned around.
  • Four sources of truth for order progress — see §7.
  • No test coverage of the frontend. The backend has 25 tests including workflow, tenant isolation and query-count regressions; the single-file React client has none.
  • The client is one 8,700-line file. Every screen, form and view lives in a single component, which makes parallel work difficult.

Suggested sequence

  1. Close the open API and rotate the remaining secret.
  2. Connect email or WhatsApp delivery for client notifications.
  3. Move the API to the database's region.
  4. Add pagination and fix the tenant-token lookup.
  5. Build the appointment and QC interfaces on the existing endpoints.
  6. Make Style DNA stable and real, or present it as illustrative.
